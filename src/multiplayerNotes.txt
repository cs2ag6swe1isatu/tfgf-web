1. Game State Synchronization (Critical)

Issue: No mechanism to sync question transitions, timers, answers, or scores across clients.

What the skill recommends:

 - Host-authoritative state with broadcast snapshots
 - Event-driven updates (start-question, answer-submit, end-question)
 - Tick-based or phase-based sync depending on gameplay

For your trivia game:

 - Host controls question timing and transitions
 - Clients display questions synchronized to host clock
 - Host collects answers and computes scores
 - Host broadcasts ranking after each question

2. Message Protocol Design

Current: 4 packet types (lobby-broadcast, join/ready/leave-request)

Needed for gameplay:

 | { type: "game-start"; payload: { questionCount: number; category: string; difficulty: string } }
 | { type: "question-start"; payload: { questionIndex: number; question: Question; startTime: number; duration: number } }

 | { type: "question-end"; payload: { questionIndex: number; correctAnswer: string; playerScores: Record<string, number> } }
 | { type: "ranking-update"; payload: { rankings: Array<{playerId: string; score: number; rank: number}> } }
 | { type: "game-end"; payload: { finalRankings: Array<{playerId: string; score: number}> } }

3. Timer Synchronization

Issue: No host clock synchronization for question timers.

Skill pattern: Host sends startTime (server timestamp), clients compute elapsed = Date.now() - startTime.

Implementation:

 - Host broadcasts question-start with server timestamp
 - Clients sync their local timer to host clock
 - Drift compensation: clients adjust if they receive a broadcast with different elapsed time

4. Loading/Waiting Phases

Issue: No intermediate states between questions or during score calculation.

Skill pattern: Use explicit phase states (lobby, playing, scoring, waiting, finished).

For trivia:

 - lobby: Waiting for players and ready state (✅ you have this)
 - playing: Active question with timer
 - scoring: Brief pause showing correct answer + per-player results
 - waiting: Between questions (optional countdown)
 - finished: Final rankings

5. Anti-Cheat & Validation

Current risk: No validation of answer timing or duplicate submissions.

Skill recommendations:

 - Server-side validation: Host checks answer-submit timestamp against question start/end
 - Reject late answers after timer expires
 - Prevent duplicate answers for same question
 - Don't trust client-side scores

6. Disconnection Handling

Issue: No graceful handling of client disconnects during gameplay.

Skill pattern: 

 - Mark disconnected players as inactive
 - Continue game for remaining players
 - Allow reconnect with state resync

Key Decision Points

 1. Tick-based vs Event-driven?
  - Recommendation: Event-driven for trivia (no continuous simulation needed)
  - Only use ticks if you add realtime features (e.g., buzzer racing)
 2. Who computes scores?
  - Recommendation: Host-authoritative (prevents cheating)
  - Host validates answer correctness and timing
  - Clients display host-computed scores
 3. Hybrid or server-authoritative netcode?
  - Recommendation: Server-authoritative (host = server)
  - Clients send intents (answers), host computes results
  - No need for client prediction in turn-based trivia
 4. UDP broadcast vs direct addressing?
  - Current: Broadcast for everything ✅ (works for LAN)
  - Future: For internet play, you'd need a relay server or Rivet Actors
